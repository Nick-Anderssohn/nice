# Handoff: fix the window frame-restore bug (sessions.json x is display-relative, y is global)

## Overall goal

Fix a window-placement bug in Nice (Rust + GPUI macOS app, this repo): when a
window's frame is saved to `sessions.json` and restored on next launch, the
saved `x` coordinate is re-interpreted as **relative to the containing
display's origin** while `y` is treated as **global** — so on multi-display
setups the window restores shifted right by the width of the display(s) left
of it, often mostly or fully off-screen. Single-display setups mask the bug
(display origin = 0).

This is a NEW task. It was discovered incidentally on 2026-07-31 while
validating 1x-display rendering fixes (that work is DONE and merged —
`origin/main` = `5f14298`). Nothing about the rendering work needs touching.

## Evidence (all observed live on Nick's machine, 2026-07-31)

Display arrangement: built-in laptop display at CG origin (0,0), UI size
1470pt wide (2x retina); Samsung C34J79x ultrawide to its right at CG x=1470
(3440x1440 at 1x scale).

Observed save→restore pairs for the same window (frame width 960):

- saved `x: 3291` → restored at CG x **4761** (= 3291 + 1470) — mostly off-screen
- saved `x: 1821` → restored at CG x **3291** (the intended global position of the first row!)
- saved `x: 2940` → restored at CG x **~4410** — partially off the ultrawide's right edge
- `y` restored where it was saved (global), e.g. `y: -20` stayed put

Interpretation: on restore, `x` gets the containing display's origin added
(or the save path subtracts it — direction unproven, see next steps), while
`y` passes through globally. The asymmetry is the bug; a correct fix makes
save and restore use ONE coordinate convention for the whole frame.

Note the restore likely picks "containing display" from the raw saved x, so
the mapping is not invertible for every target — windows in the global range
[1470, 2940) on the ultrawide could not be reached at all via the buggy math.

## Concrete next steps (ordered)

1. Find the session persistence code: grep the `nice` crate for
   `sessions.json` / `frame` / window-bounds save+restore (likely a
   sessions/persistence module in `crates/nice/src/`). Read BOTH the save
   path and the restore path.
2. Determine which side is inconsistent. Likely suspects: gpui's
   `WindowBounds`/`Bounds<Pixels>` for `open_window` may be interpreted
   display-relative by gpui (check `gpui::WindowBounds::Windowed` semantics
   and how `display_id` participates), while the save path records the
   NSWindow's global frame — or vice versa. The y behaving globally while x
   doesn't may fall out of a coordinate-flip conversion (macOS CG y-flip)
   that applies the display origin to one axis only.
3. Write a unit test on the conversion (pure math: given display frames and
   a saved frame, the restored global rect must equal the saved global rect;
   include a second-display case and a negative-y case).
4. Fix so that saved frames round-trip in GLOBAL coordinates (or convert
   consistently both ways). Handle the "saved display no longer attached"
   case by clamping onto a live display rather than restoring off-screen —
   check what the code already intends there.
5. Add backward compatibility thinking: existing sessions.json files in the
   wild were written by the OLD save path — decide whether old values need a
   migration or whether the fix makes them restore acceptably (document the
   choice in the commit).
6. Validate for real: build + `scripts/rust-install.sh` (dev) under the
